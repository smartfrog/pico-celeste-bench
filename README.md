# PICO-Celeste Bench

PICO-Celeste Bench is a coding-agent benchmark where the output is not an abstract score, but a real playable PICO-8 cartridge.

The task is to generate a complete single-screen Celeste-like platformer with dash, collisions, original level design, sprites, and a clean boot.

## Why This Benchmark Exists

This benchmark tests whether an agent can ship a small but complete interactive artifact end to end.

Plausible code is not enough. The generated `.p8` cartridge has to boot, play, look coherent, and include an original level with a dash-required obstacle.

The task is intentionally compact, but it combines many failure-prone requirements:

- strict PICO-8 cartridge file format
- responsive platformer movement
- jump and 8-direction dash mechanics
- dash recharge behavior
- solid collision handling
- spike death and respawn
- strawberry collection
- goal detection and `CLEAR!` state
- readable PICO-8 visuals based on reference assets
- original single-screen level design
- a multi-height route with elevated platforms and several required jumps
- a three-beat route with direction changes, functional hazards, and an optional berry detour
- deterministic opening autoplay that proves a route to the goal
- built-in GIF recording of the successful demo

## Geometry Oracle

Level layout is where agents burn the most effort for the least benefit: deciding whether a
jump reaches, whether a gap truly needs a dash, or whether a ledge leaves enough headroom is
arithmetic over the movement constants, and doing it in prose is slow and unreliable.
`bench/route_check.py` answers those questions directly.

Describe the level as a 16x16 grid — `.` empty, `#` solid, `^` spike, `s` spawn, `b`
strawberry, `g` goal — then:

```sh
python3 bench/route_check.py --grid level.txt                   # contract checks, instant
python3 bench/route_check.py --from-cart results/x.p8 --solve   # adds routes, a few seconds
python3 bench/route_check.py --from-cart results/x.p8 --spawn 0,12 --solve
```

The grid can live inside the cartridge, either as a comment block or as a Lua table of 16
strings; the extractor finds the first block of 16 consecutive grid rows. `--solve` replays
the prompt's exact movement constants over a small set of grounded moves (walk, walk to the
edge, jump with optional dash, ground dash) and reports:

- how each grid character was read, so a cartridge using a different legend is obvious
- landing surfaces, height bands, and the clear height above each column of each surface
- the forced gap, plus a local check that crossing it needs a dash and is possible with one
- spike groups, strawberries, spawn footing, and goal placement
- the fastest route from spawn to goal, and whether it skips the forced gap
- the intended route through the gap, as a move list with landings, berries, and update count

That move list maps one-for-one onto the phases of a state-based demo controller.

The oracle is authoritative for spacing and reach; the running cartridge stays authoritative
for gameplay. Its reach is a superset of the prompt's spacing table (for example it confirms a
3-column flat jump although the table promises only 2), so anything the table promises works.

A full `--solve` takes a second or two on a level with a route, and under ten seconds to
explore a level exhaustively when no route exists (a 16x16 grid has only a few hundred
distinct standing states). `--max-nodes` bounds the search; an exhausted search is reported as
inconclusive rather than as a contract violation.

```sh
python3 -m unittest bench.test_route_check    # 55 tests, under a second
```

## Benchmark Task

The agent must create a raw `.p8` cartridge text file. The file must start with exactly:

```text
pico-8 cartridge // http://www.pico-8.com
version 8
__lua__
```

After that, the cartridge must include a short design-notes comment, Lua code, and any required `__gfx__` or `__map__` sections.

The generated game must include:

- left/right movement
- jump
- 8-direction dash
- gravity suspended during dash
- diagonal dash normalization
- dash recharge only when grounded
- spike death and respawn
- strawberry collection and score
- visible goal flag
- `CLEAR!` message on victory
- frozen game state after victory
- at least one obstacle that requires dash
- at least four landing surfaces across three height bands, including two elevated platforms
- at least three deliberate jumps and 32 pixels of vertical progression on the main route
- varied horizontal and vertical movement with a meaningful direction reversal
- two different dash directions, two functional spike groups, and a safe breather before the climax
- an optional strawberry detour demonstrated by the autoplay
- recognizable PICO-8 Celeste-like visuals
- an opening autoplay that uses normal controls, collects exactly one strawberry, and reaches the real goal
- the configured cartridge name displayed throughout the recorded demo
- a GIF saved only after the demo reaches `CLEAR!`

Read `prompts/celeste_like.md` for the full specification.

## Running A Cartridge

You need PICO-8 installed and available on `PATH`.

To launch one of the included results:

```sh
pico8 results/fable5.p8
```

To check that a cartridge boots cleanly without interacting with it:

```sh
timeout 10 pico8 -x results/fable5.p8 2>&1
```

A clean boot prints `RUNNING:` with no `syntax error` or `runtime error` line. The timeout itself is expected because a successful PICO-8 cart keeps running.

Important: `pico8 -x` only checks boot, syntax, and startup runtime errors. It does not prove that the game is fun, beatable, or mechanically correct.

## Interactive Play-Testing (MCP)

Gameplay itself is play-tested with [pico8-mcp](https://github.com/smartfrog/pico8-mcp), an MCP server that runs a cart under deterministic, frame-by-frame lockstep control: the agent can hold buttons, advance N frames, read Lua globals (player position, deaths, win flag), and take pixel-perfect screenshots.

It copies the cart to a temp directory and injects its control harness there, so the graded `.p8` file is never modified. Example opencode configuration:

```json
{
  "mcp": {
    "pico8": {
      "type": "local",
      "command": ["node", "/path/to/pico8-mcp/dist/index.js"],
      "enabled": true
    }
  }
}
```

## Creating A New Result

Save generated cartridges in `carts/` while iterating:

```sh
mkdir -p carts
```

Then give the agent the prompt from:

```text
prompts/celeste_like.md
```

The final output should be a self-contained `.p8` file. Do not leave test harness code or debug-only changes in the final cartridge.

## Automated Benchmark Harness

The harness in `bench/` drives opencode headless to generate one cartridge per
model and collects quantitative metrics for each run. It measures production cost,
checks clean boot, and launches the final cartridge's autoplay to collect a GIF proof.
Broader gameplay and visual quality remain manually judged.

Configure the models in `bench/models.json`:

```json
{
  "repetitions": 1,
  "timeout_seconds": 1200,
  "idle_timeout_seconds": 600,
  "max_output_tokens": 48000,
  "demo_timeout_seconds": 100,
  "agent": "build",
  "prompt_file": "prompts/celeste_like.md",
  "models": [
    { "model": "voban/minimax-m3", "variant": "thinking", "out": "minimaxm3" },
    { "model": "voban/glm-5.2", "variant": "max", "out": "glm52" },
    { "model": "openai/gpt-5.5", "out": "gpt55", "cart_name": "GPT-5.5",
      "max_output_tokens": 32000 }
  ]
}
```

- `model`: OpenCode `provider/model` used for the API session.
- `variant` (optional): reasoning effort sent with the prompt (e.g. `high`, `max`,
  `thinking`). Check available variants with `opencode models <provider> --verbose`.
- `out`: stable output name. Produces `results/<out>.p8` (final cartridge) and
  `results/<out>.gif` (autoplay proof), plus `results/<out>.metrics.json` (per-model
  metrics). All three artifacts share the same `<out>` basename. It also serves as
  the display id.
- `label` (optional): prettier display text; defaults to `out`.
- `cart_name` (optional): exact title drawn inside the cart and its GIF; defaults to
  `label`, then `out`.
- `max_output_tokens`: per-turn OpenCode output limit, passed through
  `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` (OpenCode defaults to 32000). Models may override
  the global value in their own entry. The bound also covers tool-call arguments, so setting it
  too low truncates a turn that is working rather than one that is stalling: an observed run
  spent its whole first turn on a legitimate reference pass, hit a 24000 ceiling mid-analysis,
  and ended with no file on disk. The protection against an unbounded chain of thought comes
  from the prompt's rule that the cartridge exists after the first write, not from this number.
- `timeout_seconds`: maximum total attempt duration; `0` disables the total timeout.
- `idle_timeout_seconds`: maximum time without model, tool, or session progress. OpenCode
  server heartbeats prove the transport is alive but do not reset this watchdog.
- `demo_timeout_seconds`: maximum time allowed for the autoplay to create its GIF.

Run it:

```sh
python bench/run_bench.py                 # uses bench/models.json
python bench/run_bench.py --config path   # custom config
python bench/run_bench.py --dry-run       # print planned runs, do nothing
python bench/run_bench.py --quiet         # hide live model/tool activity
python bench/run_bench.py --interactive   # confirm each resume instead of resuming
```

Runs are unattended by default: an incomplete session found on disk is resumed
automatically, and a failed attempt is retried up to `max_attempts` times without asking.
Pass `--interactive` for the older behaviour that prompts before every resume. Resume
messages name the cartridge and ask the model to re-read it first, because a previous turn's
reasoning is never replayed and the file on disk is the only state that survives.

Runs are incremental by default. If `results/<out>.p8` (or the repetition-specific
name) already exists, that run is skipped and none of its `.p8`, `.gif`, or
`.metrics.json` artifacts are changed. Existing metrics are reused in the aggregate
CSV and Markdown tables when the JSON is available.

For each attempt the harness starts an isolated authenticated `opencode serve`, creates
or resumes the session through the HTTP API, and consumes the native SSE event stream.
This exposes text and reasoning deltas as they arrive, rather than waiting for a complete
assistant block. Pass `--quiet` to suppress that live activity. If a busy session stops
making progress for `idle_timeout_seconds`, the harness aborts it through the API and
preserves its id for a later resume. It then reads
`opencode export <sessionID>` (the reliable source of truth) to extract metrics.
If that export fails or is invalid, the same metrics are recovered from the raw
JSONL event stream instead.
Raw artifacts (`.stream.jsonl`, `.server.log`, `.export.json`) are written under
`results/runs/<timestamp>/` (gitignored). The final cartridge and its metrics land
in `results/` (committable), plus aggregated `results/metrics.csv` and
`results/metrics.md`.

Metrics collected per run:

| Metric | Meaning |
| --- | --- |
| `tokens_input` / `tokens_output` / `tokens_reasoning` | token usage from the session export |
| `cache_read` / `cache_write` | prompt-cache token usage |
| `tokens_total` | input + output + reasoning |
| `cost` | reported session cost in USD |
| `wall_seconds` | wall-clock time measured by the harness |
| `session_seconds` | `time.updated - time.created` from the export |
| `assistant_messages` | number of assistant turns (iterations) |
| `tool_calls_total` / `tool_calls_by_name` | tool invocations, total and per tool |
| `booted_clean` | factual `pico8 -x` clean-boot check (not a gameplay score) |
| `cartridge_written` | whether the target `.p8` file exists after the run |
| `demo_gif_written` | whether a fresh non-empty GIF was created by the final cart's autoplay |

Effort metrics, read from the raw stream and shown as a second table in `results/metrics.md`:

| Metric | Meaning |
| --- | --- |
| `reasoning_chars` | total characters of reasoning emitted across every attempt |
| `reasoning_per_tool_call` | reasoning characters divided by completed tool calls |
| `tool_calls_completed` | completed tool calls counted from the stream |
| `cart_edits` | calls to a file-writing tool (`write`, `edit`, `patch`, ...) |
| `time_to_first_tool_s` | seconds from the prompt to the first tool call |
| `time_to_first_edit_s` | seconds from the prompt to the first file edit |
| `max_no_tool_gap_s` | longest stretch with no tool call at all |

Token totals cannot distinguish a model that worked for twenty minutes from one that thought
for twenty minutes and produced nothing. These columns can. In observed runs, a healthy run
that shipped a cartridge made 49 tool calls with 5 edits and never went longer than 490s
without a tool call; a failed run emitted 135,900 characters of reasoning with **zero** edits
and a single 1,611s silence. `cart_edits` near zero together with a long silence is the
signature. The columns are recorded only — nothing in the harness reacts to them mid-run,
so every model gets identical conditions.

Delays are measured from the start of the first attempt, not from the attempt that happened to
act, so a session whose third resume finally writes a file reports the whole wait. One observed
session took 933s and three resumes to put anything on disk while `time_to_first_tool_s` stayed
at 4s — the two columns together are what separate "slow to start" from "busy but not
delivering".

Note: the clean-boot check alone does not validate gameplay. The fresh GIF proves that
the cart's authored autoplay reached its own real victory path under the prompt rules;
broader quality ranking remains a manual judgement.

## Evaluation Notes

The strongest cartridges tend to satisfy three things at once:

- they boot cleanly as raw PICO-8 cartridge files
- they are actually playable as tiny platformers
- they visually read as intentional PICO-8 games rather than rough code demos

The benchmark is deliberately small, but it is hard to fake because the final artifact can be launched and played.
